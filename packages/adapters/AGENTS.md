# packages/adapters

Adapters are the deployable packages: each runs core's handler on one platform, one folder per platform (listed in the [root `AGENTS.md`](../../AGENTS.md#layout)). These rules apply to every adapter; each adapter's own `AGENTS.md` adds its platform's specifics. A new adapter (#8, #9, #10) is a new folder here with its own `package.json` (with a `sharedidEdge` block), `tsconfig.json`, `README.md`, `AGENTS.md` and `test/`; the workspace glob, `tsc -b` references (`npm run check:projects`), TypeScript 7 check and generated docs (`npm run check:docs`) pick it up.

- **A thin adapter.** Convert the platform's request into a `Request`, call core's handler, and convert the `Response` back. Behaviour belongs in core, so every platform behaves the same; if an adapter needs a branch on behaviour, the spec is missing something.
- **Use the shared helpers; don't copy another adapter's source.** New adapters build on what the existing ones share rather than a copy of their files: `@sharedid-edge/node`'s `toWebRequest` and `sendWebResponse` for a platform that hands over Node.js requests (as Google Cloud's Functions Framework does); core's `splitHeaders` (each `Set-Cookie` kept separate), `logRequestFailure` (the catch-all that logs no request data), `handlerOrMisconfigured` (`handlerFromEnv`'s 500 on a `ConfigError`), `publicOriginFromEnv` (`SID_PUBLIC_ORIGIN`), `headerValue` (a trimmed, non-blank header) `locationWithEU` (`locationInfo` plus `isEU` from the country) and `parseHeaderMap` (a `SID_LOCATION_HEADERS`-style setting); `scripts/bundle-adapter.mjs` for the bundle, its `--bowser` and `--outdir` options and its size budget; and `conformance/src/emulator.ts` for a local stand-in. When you need something two adapters would both write, add it there (see [Duplication](../../AGENTS.md#duplication)); `npm run check:duplication` fails on copies.
- **`PlatformInfo` only from what the platform itself sets:** the connection's address, or headers the platform adds and strips from the visitor's request (`CF-Connecting-IP`, `request.cf`, `CloudFront-Viewer-*`). Never from visitor-controlled headers (`X-Forwarded-For`, location headers a client can send) unless a trust setting says so (the Node.js server's `trustProxy`), and keep that setting off by default. Validate location with core's `locationInfo`, so every platform drops the same bad values. Add new platform data to `PlatformInfo` in core, not to a module.
- **Routing follows `SID_BASE_PATH`, including `/`.** Anything in front of core that decides which requests reach it (a middleware predicate, a function route template, a CDN behaviour or route, a URL map rule, rewrites, the IaC templates) uses the configured base path, never a hard-coded `/_sid`. With the root base path, the worker owns exactly core's routes (`ROUTES`: `/sync`, `/v1`, `/optout`, `/optin`), not the whole site. Where a platform can't route that way, refuse the setting clearly (the Lambda template's `SidBasePath` pattern rejects `/`, because a CloudFront behaviour can't own just those paths without taking over the site) and document it in the adapter's README. Test the default, a custom path and `/`.
- **Every `Set-Cookie` stays a separate cookie** (`response.headers.getSetCookie()`); joining them breaks cookies.
- **The scheme decides `Secure`.** Build the request URL from the public https origin (a `publicOrigin` setting when TLS is terminated in front of the adapter).
- **Errors return no request data:** a generic 500, and logs name the error or the setting at fault, never the request. Invalid configuration gives a handler that answers every request with a 500 rather than one that sets wrong cookies.
- **Modules:** adapters build in `builtInModules` from `@sharedid-edge/modules` ([`../modules/all`](../modules/all/README.md)), so the list is the same everywhere. Never keep a list of your own; vendor modules are added by deployers at build time, not here.
- **No forwarding by default.** An adapter answers its own routes and never forwards requests to the origin. When an adapter carries a module's forwarding (a service binding, a co-located container), it follows the forwarding rules in [`../vendor-modules/AGENTS.md`](../vendor-modules/AGENTS.md#forwarding-requests-or-data): off by default, enabled per deployment with an explicit list of destination hosts, never an open proxy, prominently disclosed, preferably co-located, and never when GPC, COPPA, opt-out or consent rule it out.
- **A conformance target.** Every adapter passes the whole suite (`conformance/`), run without an account: a local server, the platform's local runtime (`wrangler dev`), or a local stand-in for the platform (`conformance/src/lambda-emulator.ts`, `vercel-emulator.ts`, `azure-emulator.ts`, `gcp-emulator.ts` in front of the real Functions Framework). Add the target to `conformance/src/targets.ts` and a script to `conformance/package.json`.
- **No account in pull-request CI.** Never add steps that deploy, or that need credentials or secrets. Templates are linted offline (`cfn-lint`, `az bicep build`, `terraform validate`); bundles are built and size-checked locally.
- **Size.** Bundled adapters are **minified** (keeping function names) and check their bundle against a size budget of **32 KB gzipped**, like the Worker and the Lambda function. The budget is this project's own, far below platform limits (Cloudflare allows 3 MB compressed on the free plan); it's there to keep cold starts and downloads small. Raise it deliberately, in its own PR, saying why.
- **Docs.** Each adapter has a full `README.md` (architecture, build, deploy, configuration and secrets, how platform data maps to `PlatformInfo`, verifying, troubleshooting) whose deployment walkthrough works without reading anything else, from prerequisites to verifying. There's no quick start in the root README any more: the adapter gets a row in its generated "Pick your platform" table from the `sharedidEdge` block in its `package.json` (`kind`, `platform`, `summary`; see [Package metadata](../../docs/development.md#package-metadata)). Run `node scripts/docs.mjs --write`; don't edit the root README.
- **Tests** cover IPv4 and IPv6 clients where the client IP matters, and the platform data mapping with recorded-style inputs.
