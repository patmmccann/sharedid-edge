# packages/adapters/cloudflare

User documentation is in [README.md](README.md); keep it in step with behaviour changes. Read [`../AGENTS.md`](../AGENTS.md) first: the rules for every adapter.

The Cloudflare Worker: `src/index.ts` (entry; builds a handler per `env` and maps `ConfigError` to a 500), `src/platform.ts` (`CF-Connecting-IP` and `request.cf` to `PlatformInfo`). The modules come from `@sharedid-edge/modules`.

- **Types.** `worker-configuration.d.ts` is generated by `npm run types` from `wrangler.jsonc` (runtime types plus `Env`). Regenerate it after changing `wrangler.jsonc` or `compatibility_date`; CI runs `npm run types:check`. Don't edit it by hand. The project uses `moduleResolution: Bundler` because Wrangler bundles the worker and the generated types assume it; every other strict setting is inherited.
- **Tests** run inside workerd through `@cloudflare/vitest-plugin` (`vitest.config.ts`). Call the worker with `exports.default.fetch(new Request(...))` from `cloudflare:workers`. Cover IPv4 and IPv6 clients where the client IP matters. `platformInfo` and `botManagementTraffic` are tested directly with plain objects; a request built with `new Request(url, { cf })` passes `request.cf` through `exports.default.fetch`.
- **`compatibility_date`** must not be newer than the workerd bundled with the installed `wrangler` and `@cloudflare/vitest-plugin`; the test pool fails to start otherwise. Bump it with those packages.
- **Configuration** lives in `vars` in `wrangler.jsonc`, as strings, with every setting listed so deployers see them. Don't add secrets to `vars`: `SID_MODULE_SECRETS` and `SID_UPSTREAM_SECRETS` are Worker secrets (`wrangler secret put`), and the conformance target passes them as `--var` only for its local run.
- **Live test environments:** `env.e2e` and `env.conformance` in `wrangler.jsonc` are this project's own [live tests](README.md#live-tests) on `sharedid.dev`. Wrangler doesn't inherit `vars`, so they list every setting; keep them in step when adding one (`npm run types` covers the types). Only `.github/workflows/e2e-cloudflare.yml` deploys them, never pull-request CI.
- **Deploying** (`npm run deploy`) needs a Cloudflare account. `npm run build` is a dry-run bundle (`wrangler deploy --dry-run`) for checking size and that it bundles.
- **Several sites:** `createWorker` passes `settingsFromEnv` (`SID_HOSTS`) and a `hostConfig` that reads Cloudflare for SaaS custom hostname metadata (`request.cf.hostMetadata.sharedid`, `HOST_METADATA_KEY`), cached by value. Core picks the configuration per host; keep that logic in core, not here.
- **Trusted upstream** (a sales house's Worker behind publishers' CDNs): `createWorker` wraps the handler in core's `withTrustedUpstream(…, trustedUpstreamFromEnv(env))`. With `SID_UPSTREAM_SECRETS` set, `CF-Connecting-IP`, `request.cf` and the custom hostname metadata describe the publisher's CDN and aren't used; core does the authentication, the forwarded headers and the host. Keep it there.
- **New platform data:** `request.cf` fields go through `platformInfo` and core's `locationInfo`, never read by a module. Add a worker test when a module depends on Cloudflare-specific data.
- **The Snippet build** (`src/snippet.ts`, `scripts/build-snippet.mjs`, `npm run build:snippet`) bundles the same handler with the settings from a JSON file and only the modules in `SID_MODULES`, for [Cloudflare Snippets](README.md#worker-or-snippet) (no `env`, no secrets, 32 KB). It bundles `ua` with Bowser only when `SID_MODULE_CONFIG` sets `ua.parser` to `bowser` (and reports the parser), refuses `ec`, `SID_MODULE_SECRETS` and trusted upstream (`SID_UPSTREAM_*`, `SID_CLIENT_IP_HEADER`, `SID_LOCATION_HEADERS`: it needs a secret), fails over 32 KB measured on the minified file (with advice on what to drop), and smoke-tests the bundle. A module added to `@sharedid-edge/modules` must also be added to its `MODULES` map (unless it needs a secret), with its settings parser, and the README's size table updated. CI builds `snippet.config.example.json` and runs `npm run test:snippet`.
- **The Snippet ships pre-validated settings.** The build resolves the settings with core's `settingsFromEnv` and runs each bundled module's parser (`MODULES`' third entry) on its `SID_MODULE_CONFIG` entry, for the deployment and each `SID_HOSTS` site; it bundles the results as literals instead of the `settingsFromEnv` call, and esbuild's `define` sets `globalThis.__SID_PREVALIDATED__` to `true`, so each module's parser returns its entry as is (it's already parsed) and the validators drop out of the bundle. Any other build leaves it unset and validates at run time, so never set it anywhere else. Invalid settings fail the build with the message the Worker would give (logged by the Worker for core settings; for a module's, the parser's message, where the Worker reports the module as an `error`). A site that doesn't run a module gets `{}` for it, which the module rejects on use, as the Worker's parser does, so `/optout` leaves that module's cookies out in both. Code only some configurations use is gated the same way: the build derives `globalThis.__SID_UNUSED_<FEATURE>__` flags from every configuration the Snippet serves (`unused` in the build script: `HOSTS` without `SID_HOSTS`; `REFLECT_PREFER`, `REFLECT_OLDER` and `REFLECT_PER_COOKIE` when no `reflect` cookie or keeper uses them), and code checks `__SID_PREVALIDATED__ === true && __SID_UNUSED_<FEATURE>__ === true`, read from `globalThis` in place (esbuild's `define` matches only that expression), so other builds keep every feature and `scripts/bundle-adapter.mjs`, which defines `__SID_PREVALIDATED__` false, compiles the check away. Only gate code that's unreachable for those settings. `scripts/test-snippet.mjs` (`npm run test:snippet`) is the check: for the conformance case files the Snippet can be built with, and for configurations of its own covering every module setting it gates, it builds the Snippet and the Worker (`src/worker.ts`, the same modules) and requires identical responses (status, headers, `Set-Cookie` without `Expires`, body without timings and minted IDs), and it checks invalid settings fail the build with the Worker's message. Add a configuration there when you add a gate or a parser.
