# packages/vendor-modules/ec

User documentation is in [README.md](README.md) (also the npm package page); keep it in step with behaviour changes. The rules for every module are in [`../../modules/AGENTS.md`](../../modules/AGENTS.md), and those for vendor modules, which this is, in [`../AGENTS.md`](../AGENTS.md).

The `ec` module (`@sharedid-edge/module-ec`): IAB Tech Lab Trusted Server Edge Cookies (`ts-ec`). See the [spec section](../../../spec/modules/ec.md) and the [Trusted Server guide](https://iabtechlab.github.io/trusted-server/guide/edge-cookies.html).

- **A vendor module, maintained by the project.** Its ID prefix is HMAC-SHA256(passphrase, normalized client IP), because that's how Trusted Server defines EC, and IP-derived IDs are for vendor modules only ([IP-derived IDs](../AGENTS.md#ip-derived-ids)). So it isn't in `builtInModules`: deployers add it as `@sharedid-edge/module-ec#ecModule`. Keep `ipDerived`, `network: "none"` and `export` in its `sharedidEdge` block, and the warning at the top of the README. Its conformance cases (`conformance/cases/module-ec*.json`) use the `vendor-modules` build, so they run on every target.
- **Stay faithful to Trusted Server's implementation.** The format, IPv6 /64 normalization, the cookie attributes (`HttpOnly`, one year, `Domain=.{domain}`), no refresh, and format-only validation all follow Trusted Server's code, which differs from its draft spec in places (the spec says not `HttpOnly`, and colon-joined IPv6). If Trusted Server changes, follow its code and note the version.
- **Drift baseline: Trusted Server at [`06e51be`](https://github.com/IABTechLab/trusted-server/tree/06e51be17074475e2dcc5e34b5a249253eff3f57).** When comparing with upstream again, diff from that commit, and update it here and in the README's "Differences from Trusted Server".
- **GDPR countries are the module's own** (`EC_GDPR_COUNTRIES`, Trusted Server's `GDPR_COUNTRIES`: EU-27, `IS`, `LI`, `NO`, `GB`; not `TR` or `CH`). `run` replaces core's `gdprApplies` with `ecGdprApplies` before `ecDecision`. Don't change core's `EU_COUNTRY_CODES` for this: it matches Cloudflare's `isEUCountry` on purpose, and governs the SharedID.
- **The EID needs TCF Purposes 1 and 4** (core segment, `purposeConsents`, as for Purpose 1: the module has no `gvlid` and doesn't use the publisher segment), as Trusted Server's `gate_eids_by_consent`; the cookie needs Purpose 1 only (`ecEidAllowed`). Keep the module's stricter rules (any TC string counts, wherever the visitor is).
- **`routes: ['v1', 'sync']`:** like Trusted Server, which sets `ts-ec` on page loads, it runs on Prebid.js's `pixelUrl` calls too. On `/sync` only the cookie (set or withdrawn) is used; the EID is ignored.
- **Output is an EID, never `ortb2.user.id`:** source `EC_EID_SOURCE` (`ts.iabtechlab.com`: OpenRTB's implementation guidance, 7.12.2, makes an alt-ID's source the domain of the party that defined it, and Tech Lab defines the EC), `atype` 1, in both `eids` and `ortb2.user.ext.eids`. `user.id` in Prebid.js first-party data would be every bidder's exchange user ID, which OpenRTB 2.6 reserves for "the exchange's user ID from its cookie" (README, "Response", has the citations). This is where we deliberately differ from Trusted Server, which sets `user.id` in requests it builds itself.
- The passphrase comes from `SID_MODULE_SECRETS` (`context.secrets`). Never return, log or put it in an error message.
- **Web Crypto only:** `crypto.subtle` HMAC, and `crypto.getRandomValues` for the suffix, with rejection sampling to keep it uniform. It uses `parseIp` from `@sharedid-edge/module-ip`.
- **Tests:** `test/ec.test.ts` has HMAC vectors computed independently with Node.js's `crypto`. Keep them independent; don't regenerate them with this module. Conformance cases are in `conformance/cases/module-ec*.json` (`module-ec-gdpr.json` for the GDPR countries and Purpose 4).
