# packages/vendor-modules/id5

User documentation is in [README.md](README.md) (also the npm package page); keep it in step with behaviour changes. The rules for every module are in [`../../modules/AGENTS.md`](../../modules/AGENTS.md), and those for vendor modules, which this is, in [`../AGENTS.md`](../AGENTS.md). Spec: [`spec/modules/id5.md`](../../../spec/modules/id5.md).

The `id5` module (`@sharedid-edge/module-id5`): the ID5 ID, fetched server-to-server from ID5's API with the deployment's own partner number, and returned as EIDs.

- **A vendor module, maintained by the project,** written from ID5's public documentation (its server-to-server API, its Prebid Server module) and Prebid.js's `id5IdSystem`, without ID5's involvement. It's the first module that sends requests from `run`, through core's `fetching` (`context.fetch`); never call `fetch` yourself. Keep `network` and `forwards` (both hosts), `export`, `gvlid` 131 and the forwarding box at the top of the README.
- **The hosts are fixed** (`ID5_HOSTS`): the `endpoint` setting may only name a URL on them, and core refuses any other host anyway. Don't add a setting that names a host.
- **Consent:** core checks ID5's vendor consent and Purpose 1 where GDPR applies (`gvlid`, `purposes`) and deletes the cache when it skips the module; `id5Denial` adds the storage decision, `us_privacy`, GPP US opt-outs (through `@sharedid-edge/module-gpp`'s `gppSignal`), and, for any TC string wherever the visitor is, ID5's vendor consent, Purpose 1 and one of Purposes 2 to 10. Any denial: no request, no ID, cache deleted. Nothing is sent without a routable client IP that `preciseLocationDenial` allows, since ID5 would otherwise see the worker's address.
- **`browsers: "webkit27"`** (opt-in) limits requests to Apple WebKit 27 or later (`isWebKit27`, conservative: when unsure, no), where the browser blocks ID5's own requests. It only decides whether a request is sent; denials and the cache are unchanged. Describe the reason in our own words; don't cite vendor decks or name vendor domains.
- **What's sent** is listed in the README's box and "The request", and in the spec. Adding a field means updating all three. The SharedID goes as `puid` only after every check has passed.
- **The cache** is the `HttpOnly` `sid_id5_<partner>` cookie: 8-hour refresh (shortened by `cache_control.max_age_sec`, never under 15 minutes), 30 days without a fresh answer, an hour's back-off after an error. It's never Prebid.js's `id5id`: Prebid.js's ID5 module needs local storage, so the output is `eids` in `/v1`.
- **Pointing it at a stub, in tests only.** The module never takes a non-ID5 endpoint: `endpoint` must be https on `ID5_HOSTS`, and core's `context.fetch` refuses anything else. Tests swap what's behind `fetch` instead, never the setting: unit tests and `e2e/server.ts` pass a stub as the handler's `forwardFetch`; conformance runs use the upstream stand-in (`conformance/src/upstream-stand-in.ts`), which answers ID5's hosts in memory or, with `CONFORMANCE_ID5_STUB`, sends them to the stub process or container (`conformance/src/id5-stub.ts`). Both live in test code no build or image includes. Don't add a runtime setting or build flag that loosens the endpoint rule.
- **Stubs everywhere except two live deployments.** Unit tests (`test/id5.test.ts`), the conformance suite (`conformance/src/upstream-stand-in.ts`, `conformance/cases/module-id5.json`), the local browser tests and every pull-request CI job use partner 173 (ID5's test partner) against stubs: never call ID5's real endpoints from them. The one exception is the live workflows on `main` (never pull requests): the Cloudflare Worker on `e2e.sharedid.dev/id5/` (`e2e-cloudflare.yml`'s `id5` jobs) and the Node.js container behind a Cloudflare publisher on `e2e.sharedid.dev/node-upstream-id5/` (`e2e-node-upstream.yml`'s `id5` jobs) run the module against ID5's real API, with partner 173 only, and their browser tests (`E2E_MODULES=id5`) check what the browser gets. Don't add other callers of the real API, or another partner number, without saying so here. The field names to confirm with ID5 for a production partner are listed in the README.
