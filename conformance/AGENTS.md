# conformance

The conformance suite is the contract between the specification and every implementation, including future ports (Rust, other platforms). Cases are JSON so any language can run them; the TypeScript runner is one implementation of the runner.

- **Case files** (`cases/*.json`) each have a `description`, the `config` (`SID_*` variables) the target must run with, and `cases`. The runner starts a target per file with that config. Files with an empty `config` are also run against live deployments (`--base-url`), so keep default-configuration cases there and others in separate files.
- **Case shape** is defined by `case-file.schema.json` and validated by `src/cases.ts` (unknown keys fail, so a typo can't silently skip an assertion). Keep the schema, the TypeScript types and the validator in step. Use `jsonAbsent` (dotted key paths) to assert that the payload leaves something out, such as precise location fields.
- **Visitor location** is sent as Cloudflare's visitor location headers (`cf-ipcountry`, `cf-region-code`, `cf-ipcity`, …). The Node.js target reads them with `SID_TRUST_PROXY`; for `wrangler dev`, `src/targets.ts` passes the same values as `request.cf` through Miniflare's `MF-CF-Blob` header, since workerd otherwise uses Cloudflare's view of the machine running the suite. Use time zones without daylight saving time so `utcoffset` doesn't depend on the date.
- **Emulated platforms map the cases' headers to their own.** A local stand-in for a platform (`src/*-emulator.ts`) drops the platform's own client IP and location headers from the client's request, as the platform does, and sets them from the case: the client IP from the connection, or with `SID_TRUST_PROXY` from the first `X-Forwarded-For` entry, and the location from the `cf-*` headers (with `SID_TRUST_PROXY`). The Lambda stand-in sets `CloudFront-Viewer-Address` and the `CloudFront-Viewer-*` geolocation headers (no continent). The Azure stand-in sets `X-Azure-ClientIP`, an `X-Azure-FDID` the handler is configured to accept (`SID_FRONT_DOOR_ID`), and every location field as the rule-set headers `SID_LOCATION_HEADERS` names (`x-sid-country`, `x-sid-region`, `x-sid-city`, …); it routes only paths the function's route template matches, and writes cookies as the Functions host does, percent-encoding their values.
- **Known platform limitations.** A case the platform itself can't pass is listed in the target's `limitations` in `src/targets.ts` (by `file#case name`, with the reason). The runner reports it as TAP `# TODO` rather than a failure, and fails if it passes, so the list can't go stale. Azure lists the two `reflect` cases whose cookie value the Functions host would percent-encode. Never list a case to hide a bug in an adapter, and say what the limitation means for publishers in the adapter's README.
- **Every behaviour in spec/SPEC.md should have a case.** Add cases with the spec change, before or with the implementation. Use fixed IDs (the suite uses `c29cb2ae-769d-42f6-891a-f53cadee823d` and `0f0e6fd3-2a43-4d0b-9e5b-0c6f5a1f8a10`) and `valuePattern` only for minted IDs.
- **`Secure`** is checked generically: present over https targets, absent over http. Don't assert it per case.
- **TC strings** in cases are generated with `tcString()` from `packages/core/test/helpers.ts`; note in the file's `description` which purposes each consents to.
- Run with `npm run conformance` (Node.js target), `npm run conformance:wrangler` (workerd through `wrangler dev`; no account needed) `npm run conformance:lambda` (the Lambda bundle behind `src/lambda-emulator.ts`, a local stand-in for CloudFront and the function URL that sets `CloudFront-Viewer-Address`) and `npm run conformance:azure` (the Azure Functions bundle behind `src/azure-emulator.ts`, a stand-in for Front Door and the Functions host). All must pass, apart from listed platform limitations. Build first (`npm run build`): the runner and the Node target run from `dist/`.
