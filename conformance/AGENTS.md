# conformance

The conformance suite is the contract between the specification and every implementation, including future ports (Rust, other platforms). Cases are JSON so any language can run them; the TypeScript runner is one implementation of the runner.

- **Case files** (`cases/*.json`) each have a `description`, the `config` (`SID_*` variables) the target must run with, and `cases`. The runner starts a target per file with that config. Files with an empty `config` are also run against live deployments (`--base-url`, whose path is the base path: the cases' `/_sid` paths move under `https://<host>/<prefix>/_sid`), so keep default-configuration cases there and others in separate files. A file a CDN in front of a deployment answers itself, before the implementation sees the request, sets `"live": false` and runs only against local targets: `request-limits.json`, since CloudFront answers a URL over 8 KB with its own `414` (on any route, opt-out included) and a 16 KB `Cookie` header with a `400`. Don't use it to skip a case a deployment fails for any other reason.
- **Case shape** is defined by `case-file.schema.json` and validated by `src/cases.ts` (unknown keys fail, so a typo can't silently skip an assertion). Keep the schema, the TypeScript types and the validator in step. Use `jsonAbsent` (dotted key paths) to assert that the payload leaves something out, such as precise location fields, and `jsonPatterns` (dotted key paths to regular expressions the whole string must match) for values that differ on every request, such as the `encrypted-ip` module's ciphertexts, whose length the pattern pins.
- **Visitor location** is sent as Cloudflare's visitor location headers (`cf-ipcountry`, `cf-region-code`, `cf-ipcity`, …). The Node.js target reads them with `SID_TRUST_PROXY`; for `wrangler dev`, `src/targets.ts` passes the same values as `request.cf` through Miniflare's `MF-CF-Blob` header, since workerd otherwise uses Cloudflare's view of the machine running the suite. Use time zones without daylight saving time so `utcoffset` doesn't depend on the date.
- **Emulated platforms map the cases' headers to their own.** A local stand-in for a platform (`src/*-emulator.ts`) drops the platform's own client IP and location headers from the client's request, as the platform does, and sets them from the case: the client IP from the connection, or with `SID_TRUST_PROXY` from the first `X-Forwarded-For` entry, and the location from the `cf-*` headers (with `SID_TRUST_PROXY`):

  | Case header | Lambda (`lambda-emulator.ts`) | Vercel (`vercel-emulator.ts`) | Google Cloud (`gcp-emulator.ts`) | Akamai (`akamai-emulator.ts`) |
  | --- | --- | --- | --- | --- |
  | client IP | `CloudFront-Viewer-Address` (`ip:port`) | `x-real-ip`, `x-forwarded-for`, `x-vercel-forwarded-for` | appended to `X-Forwarded-For` as `<client>,<load balancer>` | `request.clientIp` |
  | `cf-ipcountry` | `CloudFront-Viewer-Country` | `x-vercel-ip-country` | `x-client-region` | `userLocation.country` |
  | `cf-region-code` | `CloudFront-Viewer-Country-Region` | `x-vercel-ip-country-region` | `x-client-region-subdivision`, with the country in front (`USAZ`) | `userLocation.region` |
  | `cf-ipcity` | `CloudFront-Viewer-City` | `x-vercel-ip-city`, percent-encoded | `x-client-city` | `userLocation.city` |
  | `cf-postal-code` | `CloudFront-Viewer-Postal-Code` | `x-vercel-ip-postal-code` | none | `userLocation.zipCode` |
  | `cf-metro-code` | `CloudFront-Viewer-Metro-Code` | none | none | `userLocation.dma` |
  | `cf-iplatitude`, `cf-iplongitude` | `CloudFront-Viewer-Latitude`, `-Longitude` | `x-vercel-ip-latitude`, `-longitude` | `x-client-city-lat-long` (`lat,long`) | `userLocation.latitude`, `.longitude` |
  | `cf-timezone` | `CloudFront-Viewer-Time-Zone` | `x-vercel-ip-timezone` | none | `userLocation.timezone` |
  | `cf-ipcontinent` | none | `x-vercel-ip-continent` | none | `userLocation.continent` |

  The Azure stand-in (`azure-emulator.ts`) sets `X-Azure-ClientIP`, an `X-Azure-FDID` the handler is configured to accept (`SID_FRONT_DOOR_ID`), and every location field as the rule-set headers `SID_LOCATION_HEADERS` names (`x-sid-country`, `x-sid-region`, `x-sid-city`, …); it routes only paths the function's route template matches, and writes cookies as the Functions host does, percent-encoding their values. The Google Cloud target runs the real Functions Framework serving the bundle's `deploy/` directory, with the stand-in in front of it; both processes start per case file. The Akamai stand-in loads the bundle in a `node:vm` context without web or Node.js globals (run with `--experimental-vm-modules`), provides EdgeWorkers' built-in modules (`create-response`, `streams`, `encoding`, `crypto`, `log`) as documented (`crypto.subtle` with only the documented methods: no `generateKey`, `deriveBits`, `deriveKey` or `exportKey`, so the `encrypted-ip` module's X25519 fails there as on EdgeWorkers), and calls `responseProvider` with a request object whose `getVariable` reads `PMUSER_SID_*` from the case's `SID_*` settings; there are no platform headers to drop, since EdgeWorkers passes the client IP and location as properties. X-Forwarded-For entries after the first reach the EdgeWorker as the visitor's header, with `userLocation` and `clientIp` following them as Akamai documents or allows; `src/akamai-checks.ts` (with the TAP tally and `Cache-Control` check it shares with `fastly-checks.ts` in `src/checks.ts`), run after the suite by `conformance:akamai`, checks the EdgeWorker distrusts them, and that every response has `Cache-Control` `no-store` or `private`.

  The Fastly target isn't a stand-in: `src/fastly-viceroy.ts` runs the real Compute package (`deploy*/main.wasm`) in Viceroy, Fastly's local runtime, which takes the client address from the connection and the location from its own geolocation table, never from headers. So it relays each case's request from the case's client IP (the first `X-Forwarded-For` entry with `SID_TRUST_PROXY`; otherwise a loopback address per location, `127.0.0.1`, `127.0.0.2`, …) and writes the case's location into Viceroy's `fastly.toml` as that address's geolocation entry (Fastly's fields: `country_code`, `region`, `city`, `postal_code` in lowercase, `metro_code`, `latitude`, `longitude`, `continent`; no time zone). IPv6 addresses go to a second Viceroy on `[::1]`. The entries are seeded from the case file's requests (run.ts passes them to `startTarget`), and Viceroy restarts when a request needs a location its address doesn't have yet. The case's settings become the config store `sharedid_config`, and `SID_MODULE_SECRETS` the secret store `sharedid_secrets`. The cases' client IPs must be local addresses: on Linux, CI adds local routes for their ranges with non-local bind; elsewhere, the files that use documentation-range addresses fail with a message saying so. `src/fastly-checks.ts`, run after the suite, checks that `X-Forwarded-For` and `Fastly-Client-IP` change neither the client IP nor the location (IPv4 and `::1`), that each `Set-Cookie` arrives separately, `Cache-Control`, the 500 of a service without its config store, and that one visitor's request leaves nothing for the next: two visitors in turn, with Viceroy's log (`viceroy serve -v`, the `log` option of `startFastlyTarget`) showing one sandbox answered both in the reusable-sandbox build and a sandbox per request in the default one (it tells them apart by whether `deploy/main.js` imports `fastly:experimental`). `npm run conformance:fastly:reusable` runs the suite and the checks against the reusable-sandbox packages; CI runs both. The relay runs in the runner's process, so stopping the target stops Viceroy.

  The `docker` target isn't a stand-in either: `src/docker-nginx.ts` runs the Node.js server's container image (`SID_DOCKER_IMAGE`, default `sharedid-edge-node:conformance`, built by the root `npm run conformance:docker`) behind a real nginx (`NGINX_IMAGE`), both on the host's network, per case file. nginx gets the Node.js README's snippet (`nginxConfig`: `large_client_header_buffers 4 16k`, `location <base path>/`, `Host` passed on, `X-Forwarded-For` overwritten with `$remote_addr`, no cache), plus a `location /` to the same server standing in for the site's application, so the cases outside the base path reach it. Since nginx overwrites `X-Forwarded-For`, a relay sends each request from the case's client IP, as the Fastly relay does (`forwardFrom` in `src/emulator.ts`; local routes on Linux, as in CI); the `cf-*` location headers pass through as from Cloudflare in front. The server gets the case's settings, `SID_MODULE_PACKAGES` for `vendor-modules` (the image has every opt-in module), and `conformance/` mounted read-only with `NODE_OPTIONS=--import` of the upstream stand-in (and `no-tcf.js`), as the Node.js target preloads them.

  The Lambda@Edge stand-in (`lambda-edge-emulator.ts`, targets `lambda-edge` and `lambda-edge-viewer`) loads the bundle built `--unbaked` after setting `globalThis.__SID_EDGE__` to the case's settings (Lambda@Edge has no environment variables; a deployed bundle has them baked in), with GDPR without a location left to the client (`gdprWithoutLocation: 'client'`; the default, `applies`, is unit-tested). It sends CloudFront request events: on `origin-request`, the viewer's headers with any `CloudFront-*` replaced by CloudFront's own (`CloudFront-Viewer-Address`, the location from the case's `cf-*` headers as in the Lambda column above, `CloudFront-Forwarded-Proto: http`) and `clientIp`; on `viewer-request`, the viewer's headers as sent and `clientIp`, no location, and `SID_PUBLIC_ORIGIN` for the http URL. It checks each generated response as CloudFront would before writing it back. `lambda-edge-viewer` lists the location cases and the files that turn on `geo` (which the adapter refuses there) as limitations.

  An emulator holds only its platform's header names and event or response shapes. The rest is shared in `src/emulator.ts`: loading the bundle (`loadBundleExport`), the case's client IP (`caseClientIp`), its location headers renamed by the emulator's table (`caseLocation`, which decodes the city back to UTF-8), the body, and the server that answers a failed invocation with a 502 (`serve`). A new emulator uses them rather than copying another.

- **The real platform, emulated by AWS: `lambda-aws-emulator`** (`src/aws-emulator.ts`) deploys the Lambda bundle to [AWS Emulator](https://github.com/aws/aws-emulator), AWS's open-source local emulator of the AWS APIs, and runs the cases through its function URL: a check of `lambda-emulator.ts`, the project's own stand-in, against an AWS-built runtime and function URL. The emulator must already be running (CI installs a pinned version; see the [Lambda adapter's README](../packages/adapters/aws-lambda/README.md#on-aws-emulator)). Per case file it creates a `nodejs24.x` function from the unchanged `lambda.mjs` with the file's settings, `SID_BEHIND_CLOUDFRONT=false` (nothing is in front of the function URL) and `src/aws-emulator-runtime.ts` preloaded (the Fetch API and WebCrypto HMAC, which the emulator's runtime lacks), a public function URL, and a plain-http relay to it that drops `X-Forwarded-For` (Lambda's `sourceIp` is the connection's address, but the emulator takes it from that header). Every AWS CLI call goes to the emulator, with the credentials it writes, never to AWS. A divergence from the `lambda` target is a finding: check it against AWS's documentation before deciding whose it is.
- **A field the platform doesn't report** is listed in the target's `unavailable` payload paths in `src/targets.ts` (Vercel: `ortb2.device.geo.metro`; Google Cloud: `metro`, `zip` and `utcoffset`; Fastly: `utcoffset`, since Fastly has no IANA time zone). The runner removes those paths from `json` and `jsonIncludes` and checks they're absent instead, so the target can't pass by inventing them. List only what the platform genuinely lacks, never to skip a failure, and say so in the adapter's README.
- **Known platform limitations.** A case the platform itself can't pass is listed in the target's `limitations` in `src/targets.ts` (by `file#case name`, or a whole file by its name, with the reason). The runner reports it as TAP `# TODO` rather than a failure, and fails if it passes, so the list can't go stale. `lambda-edge-viewer` lists the cases that need a location (a viewer-request function has none) and the files that turn on `geo`, which the adapter refuses there. `lambda-aws-emulator` lists more: with no CloudFront in front there's no location, the client IP is the loopback address the suite connects from, and the emulator refuses requests with an `Origin` header or `Sec-Fetch-Site: cross-site` (the CORS cases and clickid's cross-site case). Never list a case to hide a bug in an adapter, and say what the limitation means for publishers in the adapter's README. The Lambda@Edge, Vercel, Azure, Google Cloud and Akamai targets list `trusted-upstream.json` and `cookie-domain-auto-upstream.json` as a whole: those adapters refuse trusted-upstream mode (every request is a 500), which the runner confirms by failing if any case passes. The Akamai and Fastly targets list the `encrypted-ip` cases that encrypt (`encryptedIpCases`): their Web Crypto has no X25519, and `lambda-aws-emulator` lists them too, since the value's length follows from the client IP.
- **Build options** (a file's `"build"`, one at most): `bowser`, `vendor-modules` and `no-tcf` (core's TCF decoder left out, `consent-no-tcf.json`). The bundled targets load `deploy-bowser/`, `deploy-vendor/` or `deploy-no-tcf/` (`deploy-edge-*` for Lambda@Edge), built by the root `conformance:*` scripts, and each stand-in accepts only those names; the Worker gets the matching entry point or `--define`; the Node.js server runs core unbundled, so for `no-tcf` it's started with `--import` of `src/no-tcf.ts`, which sets the same flag. A new option needs a bundle on every target. Live runs skip files with a build option.
- **Forwarding modules reach a local stand-in, never the internet.** `src/upstream-stand-in.ts` replaces `fetch` in each target's process (`src/upstream-preload.ts`, preloaded with `node --import` by every target started with Node.js, `STAND_IN` in `src/targets.ts`) and in the Worker (`targets.ts` writes a `wrangler dev` entry point, `.sharedid-modules/conformance.ts`, that imports it first), and `npm run test:snippet` imports it too. A request to a stood-in host (`*.fps.goog`, and ID5's `id5-sync.com` and `api.id5-sync.com` for the `id5` module, whose answer echoes what was sent in the EID's `ext.sent`) is answered in memory: a measurement hit with the request it received as JSON (`method`, `host`, `path`, `query`, `headers`, `body`), so cases check what was sent with `jsonIncludes` and `jsonAbsent` (`headers.x-forwarded-for`); a loopback request goes through; anything else fails. Add a new forwarding module's hosts there. **ID5 over the network:** for a case file that lists `id5`, the Node.js target runs ID5's stub (`src/id5-stub.ts`) as its own process and the `docker` target as a container next to the server's (the server's image, with `node` as the entry point), and gives the server `CONFORMANCE_ID5_STUB`, its loopback URL: the stand-in then sends requests for ID5's hosts there instead of answering them in memory, so the server's request really leaves it. That variable is read only by this test preload, which no build or image includes; the module's own rule (https on ID5's hosts) is unchanged. `src/id5-checks.ts` (`npm run conformance`, `npm run conformance:docker`) makes the requests in turn that cases can't (the cache answering the next request, nothing sent without consent) and reads what the stub received from its `GET /__requests`. The stub answers ID5's opt-out to a `ua` containing `id5-stub-optout`. The Fastly relay and AWS Emulator run their code elsewhere: Fastly refuses forwarding modules, and AWS Emulator's runtime has no `fetch`, so their forwarding cases are listed limitations (`forwardingFiles`, `NO_FETCH`). Platforms may compress a response the worker sends uncompressed (`wrangler dev` does), so a case that checks `Content-Encoding` asks for `accept-encoding: identity`.
- **Every behaviour in spec/SPEC.md should have a case.** Add cases with the spec change, before or with the implementation. Use fixed IDs (the suite uses `c29cb2ae-769d-42f6-891a-f53cadee823d` and `0f0e6fd3-2a43-4d0b-9e5b-0c6f5a1f8a10`) and `valuePattern` only for minted IDs.
- `module-data-stale.json` checks the additive `stale: true` report flag with last-good output and lookup misses, in IPv4/IPv6 and denied storage, using the vendor fixtures' fixed publication date and `maxAgeDays`. Only its two successful fixture-IP lookups are limitations on AWS Emulator (the connection is loopback); its empty lookup still checks staleness there. Scheduler/storage failure cases use fake I/O in `packages/data-updates/test`, so conformance never downloads a database or needs an account.
- **`Secure`** is checked generically, by the spec's rule (`expectsSecure` in `src/check.ts`, written from the spec rather than imported from core): present unless the origin the implementation sees is plain http on a local host. That origin is the target's `publicOrigin`: the case file's `SID_PUBLIC_ORIGIN` where the adapter reads it (`secure-public-host.json` uses a public http origin), otherwise the URL the runner calls. Don't assert `Secure` per case. In trusted-upstream mode (a file with `SID_UPSTREAM_SECRETS`), a request carrying one of its secrets is seen at the forwarded host instead (`caseOrigin` in `src/check.ts`), as the spec says.
- **Cookie domain `auto`:** the targets answer on 127.0.0.1, an IP address, so `cookie-domain-auto.json` can only check the host-only fallbacks; the hostname cases (a parent, the host itself, another site, a suffix not at a label boundary, normalization, per-site settings, a module's `auto`) are in `cookie-domain-auto-upstream.json`, through trusted upstream's forwarded host, and in core's unit tests.
- **TC strings** in cases are generated with `tcString()` from `packages/core/test/helpers.ts`; note in the file's `description` which purposes each consents to.
- Run with `npm run conformance` (Node.js target), `npm run conformance:docker` (the Node.js server's container image behind nginx, through `src/docker-nginx.ts`; needs Docker, and on Linux the cases' client IP ranges made local), `npm run conformance:wrangler` (workerd through `wrangler dev`; no account needed) `npm run conformance:lambda` (the Lambda bundle behind `src/lambda-emulator.ts`, a local stand-in for CloudFront and the function URL that sets `CloudFront-Viewer-Address`), `npm run conformance:lambda-aws-emulator` (the Lambda bundle deployed to AWS Emulator, which must be running, through its function URL), `npm run conformance:lambda-edge` (the Lambda@Edge bundle behind `src/lambda-edge-emulator.ts`, on origin-request and viewer-request events), `npm run conformance:vercel` (the Vercel bundle behind `src/vercel-emulator.ts`, a local stand-in for Vercel's proxy) `npm run conformance:azure` (the Azure Functions bundle behind `src/azure-emulator.ts`, a stand-in for Front Door and the Functions host) `npm run conformance:gcp` (the Functions Framework serving the Cloud Run function bundle, behind `src/gcp-emulator.ts`, a stand-in for the load balancer) `npm run conformance:akamai` (the EdgeWorker bundle behind `src/akamai-emulator.ts`, a stand-in for EdgeWorkers) and `npm run conformance:fastly` (the compiled Compute package in Viceroy, through `src/fastly-viceroy.ts`; needs the Viceroy binary, `VICEROY` or `viceroy` on the PATH, and on Linux the cases' client IP ranges made local, as CI does). All must pass, apart from listed platform limitations. Build first (`npm run build`): the runner and the Node target run from `dist/`.
