# conformance

The conformance suite is the contract between the specification and every implementation, including future ports (Rust, other platforms). Cases are JSON so any language can run them; the TypeScript runner is one implementation of the runner.

- **Case files** (`cases/*.json`) each have a `description`, the `config` (`SID_*` variables) the target must run with, and `cases`. The runner starts a target per file with that config. Files with an empty `config` are also run against live deployments (`--base-url`), so keep default-configuration cases there and others in separate files.
- **Case shape** is defined by `case-file.schema.json` and validated by `src/cases.ts` (unknown keys fail, so a typo can't silently skip an assertion). Keep the schema, the TypeScript types and the validator in step. Use `jsonAbsent` (dotted key paths) to assert that the payload leaves something out, such as precise location fields.
- **Visitor location** is sent as Cloudflare's visitor location headers (`cf-ipcountry`, `cf-region-code`, `cf-ipcity`, …). The Node.js target reads them with `SID_TRUST_PROXY`; for `wrangler dev`, `src/targets.ts` passes the same values as `request.cf` through Miniflare's `MF-CF-Blob` header, since workerd otherwise uses Cloudflare's view of the machine running the suite. Use time zones without daylight saving time so `utcoffset` doesn't depend on the date.
- **Emulated platforms map the cases' headers to their own.** A local stand-in for a platform (`src/*-emulator.ts`) drops the platform's own client IP and location headers from the client's request, as the platform does, and sets them from the case: the client IP from the connection, or with `SID_TRUST_PROXY` from the first `X-Forwarded-For` entry, and the location from the `cf-*` headers (with `SID_TRUST_PROXY`):

  | Case header | Lambda (`lambda-emulator.ts`) | Vercel (`vercel-emulator.ts`) | Google Cloud (`gcp-emulator.ts`) | Akamai (`akamai-emulator.ts`) |
  | --- | --- | --- | --- | --- |
  | client IP | `CloudFront-Viewer-Address` (`ip:port`) | `x-real-ip`, `x-forwarded-for`, `x-vercel-forwarded-for` | appended to `X-Forwarded-For` as `<client>,<load balancer>` | `request.clientIp` |
  | `cf-ipcountry` | `CloudFront-Viewer-Country` | `x-vercel-ip-country` | `x-client-region` | `userLocation.country` |
  | `cf-region-code` | `CloudFront-Viewer-Country-Region` | `x-vercel-ip-country-region` | `x-client-region-subdivision`, with the country in front (`USAZ`) | `userLocation.region` |
  | `cf-ipcity` | `CloudFront-Viewer-City` | `x-vercel-ip-city`, percent-encoded | `x-client-city` | `userLocation.city` |
  | `cf-postal-code` | `CloudFront-Viewer-Postal-Code` | `x-vercel-ip-postal-code` | none | `userLocation.zipCode` |
  | `cf-metro-code` | `CloudFront-Viewer-Metro-Code` | none | none | `userLocation.dma` |
  | `cf-iplatitude`, `cf-iplongitude` | `CloudFront-Viewer-Latitude`, `-Longitude` | `x-vercel-ip-latitude`, `-longitude` | `x-client-city-lat-long` (`lat,long`) | `userLocation.latitude`, `.longitude` |
  | `cf-timezone` | `CloudFront-Viewer-Time-Zone` | `x-vercel-ip-timezone` | none | `userLocation.timezone` |
  | `cf-ipcontinent` | none | `x-vercel-ip-continent` | none | `userLocation.continent` |

  The Azure stand-in (`azure-emulator.ts`) sets `X-Azure-ClientIP`, an `X-Azure-FDID` the handler is configured to accept (`SID_FRONT_DOOR_ID`), and every location field as the rule-set headers `SID_LOCATION_HEADERS` names (`x-sid-country`, `x-sid-region`, `x-sid-city`, …); it routes only paths the function's route template matches, and writes cookies as the Functions host does, percent-encoding their values. The Google Cloud target runs the real Functions Framework serving the bundle's `deploy/` directory, with the stand-in in front of it; both processes start per case file. The Akamai stand-in loads the bundle in a `node:vm` context without web or Node.js globals (run with `--experimental-vm-modules`), provides EdgeWorkers' built-in modules (`create-response`, `streams`, `encoding`, `crypto`, `log`) as documented, and calls `responseProvider` with a request object whose `getVariable` reads `PMUSER_SID_*` from the case's `SID_*` settings; there are no platform headers to drop, since EdgeWorkers passes the client IP and location as properties. X-Forwarded-For entries after the first reach the EdgeWorker as the visitor's header, with `userLocation` and `clientIp` following them as Akamai documents or allows; `src/akamai-checks.ts` (with the TAP tally and `Cache-Control` check it shares with `fastly-checks.ts` in `src/checks.ts`), run after the suite by `conformance:akamai`, checks the EdgeWorker distrusts them, and that every response has `Cache-Control` `no-store` or `private`.

  The Fastly target isn't a stand-in: `src/fastly-viceroy.ts` runs the real Compute package (`deploy*/main.wasm`) in Viceroy, Fastly's local runtime, which takes the client address from the connection and the location from its own geolocation table, never from headers. So it relays each case's request from the case's client IP (the first `X-Forwarded-For` entry with `SID_TRUST_PROXY`; otherwise a loopback address per location, `127.0.0.1`, `127.0.0.2`, …) and writes the case's location into Viceroy's `fastly.toml` as that address's geolocation entry (Fastly's fields: `country_code`, `region`, `city`, `postal_code` in lowercase, `metro_code`, `latitude`, `longitude`, `continent`; no time zone). IPv6 addresses go to a second Viceroy on `[::1]`. The entries are seeded from the case file's requests (run.ts passes them to `startTarget`), and Viceroy restarts when a request needs a location its address doesn't have yet. The case's settings become the config store `sharedid_config`, and `SID_MODULE_SECRETS` the secret store `sharedid_secrets`. The cases' client IPs must be local addresses: on Linux, CI adds local routes for their ranges with non-local bind; elsewhere, the files that use documentation-range addresses fail with a message saying so. `src/fastly-checks.ts`, run after the suite, checks that `X-Forwarded-For` and `Fastly-Client-IP` change neither the client IP nor the location (IPv4 and `::1`), that each `Set-Cookie` arrives separately, `Cache-Control`, and the 500 of a service without its config store. The relay runs in the runner's process, so stopping the target stops Viceroy.

  An emulator holds only its platform's header names and event or response shapes. The rest is shared in `src/emulator.ts`: loading the bundle (`loadBundleExport`), the case's client IP (`caseClientIp`), its location headers renamed by the emulator's table (`caseLocation`, which decodes the city back to UTF-8), the body, and the server that answers a failed invocation with a 502 (`serve`). A new emulator uses them rather than copying another.

- **The real platform, emulated by AWS: `lambda-aws-emulator`** (`src/aws-emulator.ts`) deploys the Lambda bundle to [AWS Emulator](https://github.com/aws/aws-emulator), AWS's open-source local emulator of the AWS APIs, and runs the cases through its function URL: a check of `lambda-emulator.ts`, the project's own stand-in, against an AWS-built runtime and function URL. The emulator must already be running (CI installs a pinned version; see the [Lambda adapter's README](../packages/adapters/aws-lambda/README.md#on-aws-emulator)). Per case file it creates a `nodejs24.x` function from the unchanged `lambda.mjs` with the file's settings, `SID_BEHIND_CLOUDFRONT=false` (nothing is in front of the function URL) and `src/aws-emulator-runtime.ts` preloaded (the Fetch API and WebCrypto HMAC, which the emulator's runtime lacks), a public function URL, and a plain-http relay to it that drops `X-Forwarded-For` (Lambda's `sourceIp` is the connection's address, but the emulator takes it from that header). Every AWS CLI call goes to the emulator, with the credentials it writes, never to AWS. A divergence from the `lambda` target is a finding: check it against AWS's documentation before deciding whose it is.
- **A field the platform doesn't report** is listed in the target's `unavailable` payload paths in `src/targets.ts` (Vercel: `ortb2.device.geo.metro`; Google Cloud: `metro`, `zip` and `utcoffset`; Fastly: `utcoffset`, since Fastly has no IANA time zone). The runner removes those paths from `json` and `jsonIncludes` and checks they're absent instead, so the target can't pass by inventing them. List only what the platform genuinely lacks, never to skip a failure, and say so in the adapter's README.
- **Known platform limitations.** A case the platform itself can't pass is listed in the target's `limitations` in `src/targets.ts` (by `file#case name`, with the reason). The runner reports it as TAP `# TODO` rather than a failure, and fails if it passes, so the list can't go stale. Only `lambda-aws-emulator` lists any: with no CloudFront in front there's no location, the client IP is the loopback address the suite connects from, and the emulator refuses requests with an `Origin` header (the CORS cases). Never list a case to hide a bug in an adapter, and say what the limitation means for publishers in the adapter's README.
- **Every behaviour in spec/SPEC.md should have a case.** Add cases with the spec change, before or with the implementation. Use fixed IDs (the suite uses `c29cb2ae-769d-42f6-891a-f53cadee823d` and `0f0e6fd3-2a43-4d0b-9e5b-0c6f5a1f8a10`) and `valuePattern` only for minted IDs.
- **`Secure`** is checked generically, by the spec's rule (`expectsSecure` in `src/check.ts`, written from the spec rather than imported from core): present unless the origin the implementation sees is plain http on a local host. That origin is the target's `publicOrigin`: the case file's `SID_PUBLIC_ORIGIN` where the adapter reads it (`secure-public-host.json` uses a public http origin), otherwise the URL the runner calls. Don't assert `Secure` per case.
- **TC strings** in cases are generated with `tcString()` from `packages/core/test/helpers.ts`; note in the file's `description` which purposes each consents to.
- Run with `npm run conformance` (Node.js target), `npm run conformance:wrangler` (workerd through `wrangler dev`; no account needed) `npm run conformance:lambda` (the Lambda bundle behind `src/lambda-emulator.ts`, a local stand-in for CloudFront and the function URL that sets `CloudFront-Viewer-Address`), `npm run conformance:lambda-aws-emulator` (the Lambda bundle deployed to AWS Emulator, which must be running, through its function URL), `npm run conformance:vercel` (the Vercel bundle behind `src/vercel-emulator.ts`, a local stand-in for Vercel's proxy) `npm run conformance:azure` (the Azure Functions bundle behind `src/azure-emulator.ts`, a stand-in for Front Door and the Functions host) `npm run conformance:gcp` (the Functions Framework serving the Cloud Run function bundle, behind `src/gcp-emulator.ts`, a stand-in for the load balancer) `npm run conformance:akamai` (the EdgeWorker bundle behind `src/akamai-emulator.ts`, a stand-in for EdgeWorkers) and `npm run conformance:fastly` (the compiled Compute package in Viceroy, through `src/fastly-viceroy.ts`; needs the Viceroy binary, `VICEROY` or `viceroy` on the PATH, and on Linux the cases' client IP ranges made local, as CI does). All must pass, apart from listed platform limitations. Build first (`npm run build`): the runner and the Node target run from `dist/`.
