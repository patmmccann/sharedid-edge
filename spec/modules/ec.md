# The `ec` module

Part of the [SharedID Edge specification](../SPEC.md). The general rules for modules, including consent, time limits and [modules on `/sync`](../SPEC.md#modules-on-sync), are there.

Name `ec`; no `purposes`, no `gvlid`. It runs only when listed in `SID_MODULES`, and implements IAB Tech Lab [Trusted Server Edge Cookies](https://iabtechlab.github.io/trusted-server/guide/edge-cookies.html).

- **The ID is derived from the client IP**, as Trusted Server specifies: `{HMAC-SHA256(passphrase, normalized IP), as 64 lowercase hex}.{6 random characters from A-Za-z0-9}`. Normalization: IPv4 in dotted decimal; IPv6 as its first four hextets, zero-padded lowercase hex without separators (`2001:db8:85a3::1` gives `20010db885a30000`). Clients behind the same IPv4 address or IPv6 /64 share the prefix: `2001:db8:abcd:1:1111:2222:3333:4444` and `2001:db8:abcd:1:aaaa:bbbb:cccc:dddd` both give `20010db8abcd0001`. An IPv4-mapped IPv6 address (`::ffff:a.b.c.d`) is hashed as its IPv4 address, so a dual-stack client gets the same prefix either way. Trusted Server would take its first four hextets, giving every mapped address the same `0000000000000000`.
- The passphrase is `SID_MODULE_SECRETS.ec.passphrase`, at least 32 bytes, and not a known placeholder; otherwise the module is an `error`. The placeholders, compared ignoring ASCII case, are Trusted Server's (`PASSPHRASE_PLACEHOLDERS` in `crates/trusted-server-core/src/settings.rs`: `secret-key`, `secret_key`, `trusted-server`, `trusted-server-placeholder-secret`, `replace-with-random-ec-passphrase`) and this project's own examples (`a-local-passphrase-of-at-least-32-characters`, `<openssl rand -hex 32>`, `<your passphrase>`). The error names the setting, never the value. Withdrawal (below) doesn’t depend on it: an existing `ts-ec` MUST still be deleted when the passphrase is missing or short.
- **Cookie:** `ts-ec=<id>; Max-Age=31536000; Path=/; [Domain=.<domain>;] SameSite=Lax; Secure; HttpOnly`, with `domain` from `SID_MODULE_CONFIG.ec.domain`. An existing cookie with a valid format (`^[0-9a-f]{64}\.[A-Za-z0-9]{6}$`) is used as is and not refreshed; an invalid one is replaced.
- **Output:** the EC as an EID, `{ "source": "ts.iabtechlab.com", "uids": [{ "id": <EC>, "atype": 1 }] }`, appended to the payload's `eids` and returned in `ortb2.user.ext.eids` (the fragment the page merges into Prebid.js). It MUST NOT be returned as `ortb2.user.id`: merged into Prebid.js's first-party data, that would become every bidder's exchange user ID, which OpenRTB 2.6 (Object: User) defines as "Exchange-specific ID for the user. Unless prior arrangements have been made between the buyer and the seller directly, the value in this field is expected to be the exchange's user ID from its cookie." The `source` follows the [OpenRTB implementation guidance](https://github.com/InteractiveAdvertisingBureau/openrtb2.x/blob/main/implementation.md#712---id-match-method-guidance-), 7.12.2: "In the case of universal or alt-IDs, it's the domain of the party who defined/created the ID itself." Trusted Server's code names no EID source for EC (it sets `user.id` in the OpenRTB requests it builds itself).
- **Where GDPR applies,** for this module: `gdpr=1`; or, with no `gdpr` parameter, a visitor country in the EU (27 member states), the rest of the EEA (`IS`, `LI`, `NO`) or the United Kingdom (`GB`), as Trusted Server's `GDPR_COUNTRIES` lists them, or a platform EU flag. `gdpr=0` means it doesn't apply. This list is the module's own: core's GDPR rule (EU membership, matching Cloudflare's `isEUCountry`) is unchanged. Turkey (`TR`) and Switzerland (`CH`) aren't in it, as in Trusted Server.
- **Consent:**
  - opt-out, `Sec-GPC: 1`, `coppa=1`, a `us_privacy` opt-out of sale, or a TC string without consent for Purpose 1 (core segment) **withdraws**: an existing `ts-ec` is deleted and nothing is returned. `{basePath}/optout` deletes `ts-ec` too;
  - an undecodable TC string, or GDPR applying (as above) without a TC string, fails closed: nothing is set, returned or deleted;
  - **the EID needs Purpose 4 too:** with a TC string that consents to Purpose 1 but not to Purpose 4 (use profiles to select personalised advertising, core segment), the cookie is set (or kept) as usual, but the EC is left out of `eids` and `ortb2.user.ext.eids`, as Trusted Server's `gate_eids_by_consent` does. With no TC string and GDPR not applying, the EID is returned as before.
- Its `routes` are `v1` and `sync`: an EC is set (or withdrawn) when Prebid.js calls `/sync` on a page view, as well as on `/v1`, which is closer to Trusted Server setting it on page loads. `/sync` doesn't return it.
