# Consent and opt-out

**Opt-out.** If the `_pubcid_optout` cookie is present, the worker sets no ID and expires any it finds; Prebid.js checks the same cookie. Link your privacy page to `https://www.example.com/_sid/optout` to opt a browser out, and `/_sid/optin` to undo it.

**Global Privacy Control and COPPA.** A request with `Sec-GPC: 1`, or with `coppa=1` (a site or page directed at children, as in OpenRTB `regs.coppa`), gets no ID, and any ID cookies it carries are deleted. Prebid.js doesn't call `pixelUrl` for COPPA requests, so for sync requests this only matters for other callers. Pages that fetch `/_sid/v1` themselves should add `coppa=1` when it applies.

**TCF.** Whenever a request carries a TCF TC string, the worker checks it before setting the cookie:

- **Publisher mode** (the default). SharedID is your own first-party ID, so the worker reads the **publisher** consents (the TC string's publisher TC segment): it needs consent for Purpose 1 (store and access information on a device), and consent or legitimate interest for at least one of Purposes 2 to 10. Configure your CMP to ask for publisher consent for these purposes, or it won't include a publisher TC segment and no one gets a server cookie.
- **Vendor mode.** If your company is registered as a TCF vendor, set `SID_VENDOR_ID` to your vendor ID. The worker then needs consent for that vendor, consent for Purpose 1, and consent or legitimate interest for at least one of Purposes 2 to 10, all from the vendor part of the TC string instead of the publisher segment.

When GDPR applies and there's no TC string, that counts as no consent: the worker sets nothing and deletes the ID cookies. GDPR applies when the visitor's country is one of the 27 EU member states, the rest of the EEA (Iceland, Liechtenstein, Norway), the United Kingdom or Turkey (Turkey's KVKK is treated as GDPR; Switzerland isn't on the list), or when the request says so with `gdpr=1`. The country is the platform's: Cloudflare's `request.cf.country` (and `request.cf.isEUCountry`); behind CloudFront, `CloudFront-Viewer-Country` (on Lambda@Edge, with the `origin-request` trigger; a `viewer-request` function has no location, and by default treats every visitor without a TC string as one GDPR covers: see [GDPR without a location](../packages/adapters/aws-lambda/README.md#gdpr-without-a-location)); on Vercel, `x-vercel-ip-country`; behind Azure Front Door, the country its rule passes on; behind Google Cloud's load balancer, `{client_region}`; on Akamai and Fastly, the platform's geolocation; for the Node.js server, the country in its trusted proxy's location headers; in [trusted-upstream mode](configuration.md#trusted-upstream-behind-a-publishers-cdn), the country the publisher's CDN passes on. `gdpr=0` overrides the location. The conformance cases check each country on every platform; the live tests also request each live setup from a real address in Germany, the [EU visitor](../packages/adapters/aws-lambda/README.md#the-eu-visitor), so the platform's own location decides ([what that has shown](verification.md#check-eu-visitor)).

The TC string comes from a `gdpr_consent` parameter, or else the CMP's `euconsent-v2` cookie. **Set `pixelConsent: true` in Prebid.js** (11.53.0 and later; see [Configure Prebid.js](prebid.md)): Prebid.js then adds the consent it has to the sync route (`gdpr`, `gdpr_consent`, `us_privacy`, `gpp`, `gpp_sid`), so the worker decides with exactly the consent Prebid.js used: the TC string even when your CMP keeps it only in local storage, your CMP's `gdprApplies` (`gdpr=1` or `gdpr=0`, which overrides the location), and the GPP string of a GPP-only CMP. Without it, or on older Prebid.js versions, the sync carries no consent, so **your CMP must store the TC string in the `euconsent-v2` cookie** (check yours: some keep it only in local storage). Without either, EU visitors get no server cookie, which is the safe failure.

**Builds without the TCF decoder.** Every default build decodes TC strings. A deployment that never needs TCF (no visitors where GDPR applies, or consent decided another way) can leave the decoder out to save about 1.6 KB minified (0.6 KB gzipped): `--no-tcf` on the [Cloudflare Snippet's build](../packages/adapters/cloudflare/README.md#leaving-tcf-out), where it matters most (32 KB), or on a bundled adapter's build (`npm run bundle -w @sharedid-edge/aws-lambda -- --no-tcf`, and the same for Vercel, Azure, Google Cloud, Akamai and Fastly). That build can't read a TC string, so a request that carries one, from `gdpr_consent` or the `euconsent-v2` cookie, is treated as one it can't read: no SharedID, existing ID cookies deleted, no precise location, whatever `gdpr` says (`X-SharedID-Status: denied: tcf: TC string not decoded (build without TCF)`). It never allows storage it would otherwise deny. Everything else is unchanged: where GDPR applies without a TC string nothing is stored, and elsewhere the ID is set. So leave TCF out only if your visitors don't carry TC strings; if your CMP writes `euconsent-v2`, keep the default build.

**CMPs without a TC string.** Many CMPs, especially WordPress ones, write no TC string: Complianz, CookieYes, Borlabs Cookie, iubenda, and Cookiebot or OneTrust with TCF off. The opt-in [`cmp` module](../packages/modules/cmp/README.md) reads their own consent cookie instead. A visitor who refused in your CMP gets no SharedID, and loses an existing one, wherever they are and even with a TC string that allows it; one who accepted gets the SharedID where GDPR applies and there's no TC string. GPC, COPPA and the opt-out cookie still come first, a TC string that denies still denies, and a cookie the module can't read, or one written before the visitor chose, changes nothing. A refusal shows as `X-SharedID-Status: denied: cmp: <cmp>: no consent for <category>`. It's opt-in at build time: add it to your build, then list it in `SID_MODULES` (its README has the steps for each platform, and the cookie formats).

**US privacy opt-outs (GPP).** The worker reads the `gpp` and `gpp_sid` parameters but doesn't decode the GPP string itself. The opt-in [`gpp` module](../packages/modules/gpp/README.md) does, for the US sections `gpp_sid` lists (US National and the state sections): a visitor who opted out of sale, sharing or targeted advertising there, or a known child without consent, gets no SharedID and loses an existing one, exactly as with GPC (`X-SharedID-Status: denied: gpp: usnat: opted out of sale`). A string it can't read for such a section denies too, the conservative reading; no opt-out changes nothing, and sections `gpp_sid` doesn't list, and non-US ones, are ignored. It can only deny, so it never weakens GPC, COPPA, the opt-out cookie or a TC string. It only sees requests that carry `gpp` and `gpp_sid`: Prebid.js's sync with `pixelConsent: true` (11.53.0 and later, with Prebid.js's GPP consent management module), and your own calls to `/_sid/v1` or `/_sid/sync` with your CMP's values; there's no standard GPP cookie to read. It's opt-in at build time, like `cmp`.

**The order.** Storage is decided in this order, the first that applies winning: the opt-out cookie; GPC and COPPA; a refusal from a consent module such as `cmp` or `gpp`; a TC string; a grant from a consent module; GDPR applying (no consent); otherwise allowed. The [specification](../spec/SPEC.md#opt-out-and-consent) has the details, and [Consent providers](../spec/SPEC.md#consent-providers) the rules any such module follows (the same hook will carry Google Consent Mode).

**Deleting the cookie.** When consent is missing or withdrawn, or with GPC, COPPA or opt-out, the worker deletes the ID cookies it finds: it overwrites each with an empty value, `Max-Age=0` and an `Expires` date in 1970, which browsers treat as a delete. With `SID_COOKIE_DOMAIN` set, it deletes a host-only copy too.

**Server-side Google Tag Manager** gets consent from Google Consent Mode, which never reaches the worker. To keep the two consistent, see [Consent: keeping Consent Mode and SharedID Edge consistent](sgtm.md#consent-keeping-consent-mode-and-sharedid-edge-consistent).

**What's stored and logged.** SharedIDs are random UUIDs, never derived from the IP address or other request data. (Opt-in modules marked "IP-derived ID" in the [module index](modules.md#module-index), such as `ec`, set their own IP-derived IDs: see each module's README.) The worker stores nothing server-side and logs nothing about requests (Workers observability is off in the default config). A platform rate limiting rule, or the Worker's opt-in rate limiting bindings, keeps counters keyed by IP address at the platform for its window ([Abuse protection](abuse-protection.md)).
