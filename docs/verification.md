# How SharedID Edge is verified

Every way of deploying SharedID Edge is checked somehow, but not all in the same way. The Cloudflare Worker is deployed to a real Cloudflare zone and tested there after every merge, while the Akamai EdgeWorker has only run behind this project's own stand-in for Akamai. This page says, for every deployment in the adapter READMEs and the [hosting-company](hosting-companies.md) and [upstream-operator](upstream-operators.md) guides, how it has been verified, what that proves, and where to look at the results yourself.

This page is the overall picture. The guides' "What's been verified live" sections keep the details of each live run, and link here.

## The verification levels

Each deployment below has one of five levels, the highest it has reached **as a whole**, set up as its guide says. When parts of a deployment have been checked at a higher level than the whole (the handler emulated, say, but the CDN rule in front of it only written from the vendor's documentation), the table gives the lower level and lists the parts in its evidence.

| Level | What it is | What it proves | What it can't prove |
| --- | --- | --- | --- |
| **1. Live, automated** | A GitHub Actions workflow deploys to real infrastructure in this project's own account and tests it there, on every merge to `main`, nightly and on demand. The run history is public. | That the deployment steps work. Also the platform's real routing and headers (`request.cf`, the visitor's address and location), TLS, the real runtime, that the endpoint shares the site's IP addresses (Safari's rule), the CDN not caching responses, and unmodified Prebid.js on a page from the same hostname in three browser engines. It keeps proving it: a change on the platform's side, or a new browser version, fails the nightly run. | Anything outside the test's vantage point. The runs come from GitHub's runners in the US, so GDPR decided by a real visitor's country comes from the [EU visitor](#check-eu-visitor), a function in Frankfurt that the live workflows run. Only one configuration per deployment is tested (the default, and the browser tests' settings), the test zone is on Cloudflare's Free plan (no Bot Management, no Snippets), and real Safari isn't in the live runs. |
| **2. Live, manual** | Someone ran the project's scripts against real infrastructure by hand, and the result is recorded with its date in an issue, a pull request or a guide. | The same as level 1, for that configuration, on that date. | That it still works: nothing re-runs it. A platform change since the recorded date isn't caught. The same vantage-point limits as level 1 apply. |
| **3. Emulated** | The real build runs in the vendor's own local runtime or official emulator: the Worker in workerd through `wrangler dev`, the compiled Fastly package in Viceroy, or the Lambda bundle on AWS Emulator. For a self-hosted deployment, the real thing on one machine: the Node.js server's container image behind a real nginx, configured as its README says. In CI or locally, with no account. | That the bundle the deployment uses actually runs in that runtime: its APIs, globals, module format, size limits and cookie handling. It runs the whole conformance suite, every configuration, including cases a live run can't set up (an EU location, IPv6 clients, forged headers, other settings). | The platform's network edge. The runtime is real, but the visitor's address and location are fed in by the test, not by the platform. Its real header behaviour, TLS, IP-address sharing with the site, caching, and the deployment steps themselves aren't exercised. |
| **4. Simulated** | The handler runs behind this project's own stand-in for the platform (`conformance/src/*-emulator.ts`), which converts HTTP requests to the platform's event or request shape and the response back, plus unit tests with requests shaped as the platform delivers them. | That the adapter maps requests and responses as the platform's documentation describes: the client IP and location headers it reads, how cookies leave it, its routes, and the settings it refuses. The whole conformance suite passes, with the platform's known gaps listed. | That the platform behaves as documented. The stand-in was written from the same documentation as the adapter, so a misreading in both passes. Nothing proves the real headers, the real runtime (for the stand-ins that aren't the vendor's code), the visitor's real address and location, TLS, IP sharing (Safari's same-IP rule), caching or the deployment steps. |
| **5. Documented only** | A configuration written from the vendor's documentation, not run in any of the ways above. | Nothing beyond review. | Anything. Check it with [Verifying your own deployment](#verifying-your-own-deployment) before relying on it. |

Static checks don't raise a level on their own: CI lints the AWS templates with `cfn-lint`, builds the Azure Bicep templates and validates the Google Cloud Terraform, all without an account. They catch syntax and schema errors, not whether the platform accepts the template or behaves as expected.

### Live tests (Cloudflare)

[`e2e-cloudflare.yml`](../.github/workflows/e2e-cloudflare.yml). Details in the Cloudflare adapter's [Live tests](../packages/adapters/cloudflare/README.md#live-tests).

- **Trigger:** every push to `main` (a merged pull request), nightly at 04:17 UTC, and on demand (*Run workflow* on the Actions tab). Never on pull requests. Runs don't overlap; of several waiting, only the newest runs.
- **Infrastructure:** the test zone `sharedid.dev`, on Cloudflare's Free plan. Three Workers: `sharedid-edge-e2e` on `e2e.sharedid.dev/_sid/*` (the `e2e` environment in `wrangler.jsonc`: no pixel caching, `reflect` with `uid1` and `_ga`, and `clickid`); `sharedid-edge-e2e-site` on `e2e.sharedid.dev/*` (the test page and a Prebid.js bundle of a typical publisher setup, from `e2e/site/`); and `sharedid-edge-conformance` on `conformance.sharedid.dev/_sid/*` (the default configuration).
- **Steps:** deploy the three Workers; wait until both hostnames answer; [`verify-deployment`](#verify-deployment) against `https://e2e.sharedid.dev`; the [conformance suite](#the-conformance-suite)'s default-configuration cases (26) against `https://conformance.sharedid.dev/_sid`; then the 14 [browser tests](#the-browser-tests) against `https://e2e.sharedid.dev`, with cookie domain `sharedid.dev`, in Chromium, Firefox and WebKit, each its own job. With the AWS role (`AWS_E2E_ROLE_ARN`), [`check-eu-visitor`](#check-eu-visitor) against `https://e2e.sharedid.dev/_sid`; without it, that job is skipped.
- **What a pass proves:** on Cloudflare's real edge, as of that run, the route on the site's own hostname answers from the site's IP addresses (Safari's rule); the cookies are `Secure`, long-lived and set by the server, on the right domain; an existing ID is kept and restored; denied consent, GPC, COPPA and opt-out set nothing and delete what's there; and unmodified Prebid.js gets and keeps a server-set SharedID in three browser engines.
- **What it doesn't:** see level 1 above: one vantage point in the US, the default and browser-test configurations only, no CORS or forged-header checks, no real Safari.
- **A failure** after a merge or overnight opens an issue titled "Live Cloudflare tests are failing", or comments on the open one; a later green run on `main`, including a re-run of the failed jobs, closes it as completed ([`.github/actions/live-issue`](../.github/actions/live-issue/action.yml)). When a browser job failed because the Ubuntu apt mirrors were down, the issue says so ([Installing the browsers](#the-browser-tests)), so it isn't taken for a regression; this holds for every live workflow. The browser jobs upload `playwright-report-live-<browser>` on failure, kept for 7 days.
- **Inspect it:** [Actions → Live tests (Cloudflare)](https://github.com/patmmccann/sharedid-edge/actions/workflows/e2e-cloudflare.yml). Each run's log shows `verify-deployment`'s checks and the suite's TAP output case by case.

### Live tests (upstream operator)

[`e2e-upstream.yml`](../.github/workflows/e2e-upstream.yml). Details, and the setup checklist, in the Cloudflare adapter's [upstream operator and SaaS workflow](../packages/adapters/cloudflare/README.md#the-upstream-operator-and-saas-workflow).

## What the checks assert

### verify-deployment

[`scripts/verify-deployment.ts`](../scripts/verify-deployment.ts), `npm run verify-deployment -- --site https://www.example.com [--endpoint …]`. It checks a deployment from outside, as a browser sees it:

1. **DNS:** the endpoint is on the site's own hostname, or its host shares at least one IP address with the site's (Safari caps cookies from a server whose address doesn't match the site's). Not `https` fails.
2. **`/_sid/sync`, as Prebid.js calls it on a first visit,** with a fresh ID: `200 image/gif`; sets `_pubcid` with that ID (adopted, not replaced), a `Max-Age` of at least 300 days, `Secure`, `SameSite=Lax`, not `HttpOnly`, and a `Domain` that covers the site; sets the `_pubcid_sv` recovery copy `HttpOnly` (a warning if it's off); not served from a shared cache (`cf-cache-status`, `x-cache` or `age`).
3. **`/_sid/v1`** returns payload version 1.

### check-cloudfront

[`scripts/check-cloudfront.ts`](../scripts/check-cloudfront.ts), for the AWS live tests only, against a function with `SID_MODULES=ip,geo,ua,bot` and an allowed origin: `/v1` answers through CloudFront (`x-amz-cf-pop`); caching is off (two requests, two new IDs, no cache hit); the client IP is the address `checkip.amazonaws.com` sees; there's a `device.geo` country; Chrome's Client Hints become `device.sua`; `Accept-Language` arrives (no likely bot); forged `CloudFront-Viewer-*` and `X-Forwarded-For` are replaced; the allowed origin gets CORS and another doesn't; `Sec-GPC: 1` gets `denied: gpc` and no ID; and, with `--function-url`, the function URL refuses direct requests.

### check-live-site

[`scripts/check-live-site.ts`](../scripts/check-live-site.ts), for the upstream-operator, SaaS and Vercel live tests: `npx tsx scripts/check-live-site.ts --site https://<site> --cookie-domain <domain> [--endpoint https://<upstream endpoint>] [--unlisted https://<unlisted hostname>]`, against a site whose SharedID Edge runs `ip` and `geo`. `/_sid/v1` has the address two echo services see, and a country; forged `X-SID-Client-IP`, `X-SID-Country`, `X-SID-Region`, `X-SID-Upstream-Auth`, `X-Forwarded-Host`, `X-Forwarded-For`, `X-Real-IP` and Vercel's `X-Vercel-Forwarded-For`, `X-Vercel-IP-Country`, `X-Vercel-IP-Country-Region` and `X-Vercel-IP-City` change nothing in `/_sid/v1` or `/_sid/sync` (the same address and location, the cookie on the same domain, GDPR not decided by a forged `DE`); `/_sid/sync` sets `_pubcid` with `Domain=<domain>`. With `--endpoint`, `/_sid/v1` and `/_sid/sync` on the endpoint itself answer `403` with no cookie, with no headers and with a forged secret, forwarded host, client IP and country. With `--unlisted`, both answer `404` with no cookie on a hostname that isn't in `SID_HOSTS`.

### check-eu-visitor

[`scripts/check-eu-visitor.ts`](../scripts/check-eu-visitor.ts), the live workflows' `eu-visitor` jobs: `npx tsx scripts/check-eu-visitor.ts --target https://<site>/_sid [--geo https://<site with geo>/_sid …]`. It invokes the function `sharedid-eu-visitor` in eu-central-1 (the Lambda adapter's [EU visitor](../packages/adapters/aws-lambda/README.md#the-eu-visitor)) with `aws lambda invoke`, so every request comes from a German address and the CDN in front of each site sees a German visitor. First, Cloudflare's `/cdn-cgi/trace` must place the function in an EU member state. Then, for each site, with no `gdpr` parameter, so GDPR follows from the platform's own location: `/_sid/v1` and `/_sid/sync` without a TC string answer `denied: tcf: GDPR applies and there is no TC string`, with no ID and no `Set-Cookie`; with `consent.json`'s TC string that consents to Purposes 1 and 2, `/_sid/v1` returns an ID and sets `_pubcid` to it and `/_sid/sync` sets the ID Prebid.js sends; with `--geo`, `device.geo.country` is an EU member state (any, not only Germany). On Cloudflare, no response shows `request.cf.isEUCountry` itself: GDPR follows from it or from the country, and for Germany both say so.

**Recorded result: live, automated.** The `eu-visitor` job first passed in the AWS, Cloudflare and upstream-operator live workflows on 17 November 2026, on the push after it was merged: AWS ([run](https://github.com/patmmccann/sharedid-edge/actions/runs/44024534777)), Cloudflare ([run](https://github.com/patmmccann/sharedid-edge/actions/runs/44024534472)) and the upstream operator ([run](https://github.com/patmmccann/sharedid-edge/actions/runs/44024534410)). Before that, the first run from Germany, by hand the same day, after deploying the function with `live/eu-visitor.sh`, passed all 29 checks against six targets. Cloudflare's trace placed the function at `loc=DE`. On `https://e2e.sharedid.dev/_sid` (Cloudflare Worker), the CloudFront test site's `/_sid` and `/_sid-platform`, `saleshouse-pub.sharedid.dev` (Cloudflare publisher recipe), `pub.hotba.be` (CloudFront publisher recipe) and `saas.hotba.be` (Cloudflare for SaaS), each with no `gdpr` parameter: `/_sid/v1` and `/_sid/sync` without a TC string answered `200`, `denied: tcf: GDPR applies and there is no TC string`, no ID and no `Set-Cookie`; with consent, `/_sid/v1` returned an ID and set `_pubcid` to it, and `/_sid/sync` set the ID Prebid.js sent; on the four targets with `geo`, `device.geo` was `DEU`, region `HE` (Hesse).

### The conformance suite

The contract every implementation passes ([`conformance/`](../conformance/AGENTS.md)): JSON case files in `conformance/cases/`, each with the settings its target runs with.

- **Against a local target** (`--target node|docker|wrangler|lambda|lambda-aws-emulator|vercel|azure|gcp|akamai|fastly`), every case file runs, each with its own settings: consent, GDPR by location, routes and CORS, cookie options, `SID_HOSTS`, trusted-upstream mode, forged headers without it, and every module. Forwarding modules' requests go to a local stand-in (`conformance/src/upstream-stand-in.ts`), installed in each target's process or Worker isolate, which also refuses any other request that would leave the machine. A file with `"build"` runs against that build of the target: Bowser, the opt-in modules, or no TCF decoder (`consent-no-tcf.json`, built `--no-tcf`; the Node.js server, which isn't bundled, sets the same flag before it loads). A case a platform can't pass is listed with its reason in `conformance/src/targets.ts` and reported as `# TODO`; the run fails if a listed case starts passing.
- **Against a deployment** (`--base-url https://…/_sid`), only the files with the default configuration run, since a deployment has one: `consent.json` (15 cases) and `sync.json` (11), 26 in all. They need no client IP or location of their own, which a live run can't choose. `request-limits.json` has the default configuration too, but is marked `"live": false`: a CDN in front answers oversized requests with its own limits before the worker sees them (CloudFront answers a URL over 8 KB with its own `414`, on any route, and a 16 KB `Cookie` header with a `400`), so it runs against every local target only.

### The browser tests

[`e2e/tests/prebid-sharedid.spec.ts`](../e2e/tests/prebid-sharedid.spec.ts): 25 Playwright tests, each run in Chromium, Firefox and WebKit, except one WebKit skips since it reports no response status (so "74 of 74" is all of them), with unmodified Prebid.js (a bundle of a typical publisher setup at the version `e2e/package.json` pins, with `pixelConsent: true`) and static TCF and GPP consent data. Three need the opt-in `gpp` module, which the live deployments don't build, and two check the demo page with GitHub's API stubbed, so those run locally only (20 run live). They read requests and cookies from the browser's side, so the same tests run locally and against a live site (`E2E_BASE_URL`, `E2E_COOKIE_DOMAIN`). They check:

- a first visit's ID, minted by Prebid.js and sent to `pixelUrl`, comes back as a server-set `_pubcid` lasting more than 360 days, with an `HttpOnly` `_pubcid_sv`, and Prebid.js reads it; a second visit keeps it;
- there's one `_pubcid`, on the expected domain;
- with consent, GDPR applies and both cookies are set; without purpose 1 consent, neither Prebid.js nor the endpoint stores an ID, and the endpoint deletes what an earlier visit left (`denied: tcf: no publisher consent for purpose 1`); where GDPR doesn't apply, everything works;
- with `pixelConsent`, the sync's query string is exactly `id`, then the consent Prebid.js has (`gdpr=1&gdpr_consent=…`, `gdpr=0`, or `gpp=…&gpp_sid=7` from a GPP-only CMP); with no `euconsent-v2` cookie, the endpoint sets or denies the ID as `gdpr_consent` says, and `gdpr_consent` wins over a cookie that allows storage; a US National opt-out of sale in `gpp` makes the endpoint delete the ID cookies (locally, with the `gpp` module); without `pixelConsent`, the endpoint still reads `euconsent-v2`;
- a cleared script cookie is restored from the recovery copy;
- `pbjs.getUserIdsAsync()` resolves on a later visit;
- the `reflect` module refreshes and restores a vendor's `uid1` and `_ga` (four tests), and `clickid` keeps a landing page's `gclid` for 90 days;
- after an opt-out, the endpoint sets no ID cookies;
- the page's results panel (below) shows every browser-side check green, and, when asked, the worker's `/_sid/v1` agreeing and the `HttpOnly` copy restoring a deleted `_pubcid`; it fails the sync check when the endpoint answers Prebid.js with an error, and its own `/_sid/v1` call carries the sync's consent, so a GPP opt-out stays opted out; the demo's AWS tile turns red when that deployment's EU visitor fails, and a tile says when it last checked and "Check again" skips its cache.

**See it yourself.** The test page has a results panel ([`e2e/site/public/results.js`](../e2e/site/public/results.js)) that shows a person what happened in their own browser: Prebid.js's `pixelUrl` call, the server-set `_pubcid` and its expiry as the browser stores it (where the browser exposes it, as Chrome and Safari 18.4 and later do), the EIDs Prebid.js adds to bid requests, the worker's `/_sid/v1` answer (its debugging headers, and the IP and location modules' output where they're on), and a button that deletes `_pubcid` and has the worker restore it from the `HttpOnly` copy. [The live demo](https://e2e.sharedid.dev/demo/) ([`e2e/site/public/demo/`](../e2e/site/public/demo/index.html), deployed with the test site by the [Cloudflare live tests](#live-tests-cloudflare)) links to every live deployment's copy of that page, and shows the latest run of each live workflow on `main` (the sGTM and real-Safari checks run only in CI, so their tiles show the run alone). GitHub allows 60 unauthenticated API requests an hour per address, so the demo keeps each answer in your browser for ten minutes: each tile says when it last asked GitHub ("Checked 3 min ago"), and **Check again** asks again straight away, skipping that cache, which uses two of those requests per tile.

[`e2e/tests/cookie-domain-auto.spec.ts`](../e2e/tests/cookie-domain-auto.spec.ts) checks [`SID_COOKIE_DOMAIN=auto`](configuration.md#cookie-domain-auto) with Prebid.js's `pixelCookieDomain` (11.53.0 and later), locally only, since each case is a site of its own on the local server: with `auto`, the sync carries `cookie_domain=sharedid.test` from a page on `auto.sharedid.test` and the cookies go on that parent; without `pixelCookieDomain` they're host-only; a fixed domain and `host-only` ignore `cookie_domain`; and an upstream operator's endpoint in trusted-upstream mode with `auto` gives two publishers (`www.pub-a.test`, `www.pub-b.test`, forwarded by the local server playing their CDN) each their own domain.

WebKit isn't Safari: it doesn't apply Safari's 7-day cap on script-set cookies, so the tests clear the cookie to simulate one. [`e2e/safari/safari.test.ts`](../e2e/safari/safari.test.ts) runs five of the core tests in real Safari ([Real Safari](../e2e/AGENTS.md#real-safari)), in CI against the local server only.

**Installing the browsers.** Every browser job, in CI and the live workflows, installs its browser through [`.github/actions/install-browser`](../.github/actions/install-browser/action.yml) ([`e2e/install-browser.sh`](../e2e/install-browser.sh)): the browser from Playwright's CDN, then its system packages from `.deb` files cached per runner image, or through apt (with a second Ubuntu mirror) when the cache has none for that image, caching what it downloads. If the Ubuntu mirrors are down and the browser is missing a library, the job fails at that step, before any test, with an "apt outage" error naming the libraries, and the live workflows' issue or comment adds "Infrastructure: apt outage (...), not a regression". Re-run the failed jobs once the mirrors are back. Such a failure says nothing about SharedID Edge.

- **The Lambda@Edge live jobs running green,** once the role has the Lambda@Edge statements and `AWS_LAMBDA_EDGE_ENABLED` is set ([#177](https://github.com/patmmccann/sharedid-edge/issues/177)); then both Lambda@Edge rows move to level 1.
- **Fastly, Akamai, Azure and Google Cloud** on live accounts, and the Fastly, Akamai, nginx, HAProxy and Azure Front Door publisher recipes. Each adapter's README lists what a first deployment should check.
- **SharedID Edge beside server-side GTM,** on Cloudflare or in containers, and the variable template in a real server container. [#20](https://github.com/patmmccann/sharedid-edge/issues/20). The [sGTM tests](#the-sgtm-tests) cover the container part once the `SGTM_CONTAINER_CONFIG` secret is set ([#26](https://github.com/patmmccann/sharedid-edge/issues/26)).
- **Real Safari against a live deployment:** it can run against one by hand (`E2E_BASE_URL=… npm run test:safari` on a Mac), but no run is recorded.
- **The JA4 TLS fingerprint** behind the `bot` module's [`ja4Mismatch`](../packages/modules/bot/README.md#ja4-fingerprint-that-contradicts-the-user-agent), on any platform. Only three supply one, and none of the live runs can produce it: Cloudflare's `request.cf.botManagement.ja4` needs Bot Management, an Enterprise add-on the test zone doesn't have; Fastly's `event.client.tlsJA4` is `null` in Viceroy, and Fastly has no live run; CloudFront's `CloudFront-Viewer-JA4-Fingerprint` needs a custom origin request policy (`SID_CLOUDFRONT_JA4=true`), which the AWS live tests don't use. Each adapter's mapping is unit-tested with JA4 values from FoxIO's public mapping (`npm run test:snippet` also feeds it to the Snippet), and `conformance/cases/module-bot-ja4.json` checks on every target that without a platform JA4 nothing is decided and a visitor's JA4 header is ignored. Lambda@Edge, Vercel, Azure, Google Cloud, Akamai and the Node.js server supply none.

If you run SharedID Edge on one of these, [an issue](https://github.com/patmmccann/sharedid-edge/issues) with what you checked and saw moves it up this page.

## Verifying your own deployment

Whatever its level here, check your own deployment before relying on it, with the same tools:

```sh
npm ci && npm run build
npm run verify-deployment -- --site https://www.example.com
node conformance/dist/run.js --base-url https://www.example.com/_sid      # on a deployment with the default settings
curl -s https://www.example.com/_sid/v1                                   # with ip and geo on: your own address and location
```

And with the browser tests (`npm ci --prefix e2e`, then in `e2e/`): `E2E_BASE_URL=https://www.example.com E2E_COOKIE_DOMAIN=example.com npx playwright test`, on a page that loads Prebid.js as the test site does. Each adapter's README has a Verify section with the platform's own checks.
